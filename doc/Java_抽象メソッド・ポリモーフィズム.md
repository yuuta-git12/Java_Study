# Java 抽象メソッドとポリモーフィズム まとめ

## 1. 抽象メソッドに `static` は付けられない

```java
abstract class Sample {
    abstract static void method(); // コンパイルエラー
}
```

### なぜ両立できないのか

| | abstract | static |
|---|---|---|
| 束縛のタイミング | 実行時(動的束縛) | コンパイル時(静的束縛) |
| 呼び出し方法 | インスタンス経由でオーバーライドされたメソッドが呼ばれる | クラス名経由で決まったメソッドが呼ばれる |
| 目的 | サブクラスでの実装(ポリモーフィズム)を強制する | クラスに属する処理で、オーバーライドの対象にならない |

- `abstract` は「サブクラスが実装し、実行時に動的に呼び分けられる」ことが前提
- `static` は「クラスに固定的に紐づき、オーバーライドできない(隠蔽にしかならない)」

→ 設計思想として矛盾するため、Java言語仕様でコンパイルエラーとして禁止されている。

### 参考:staticメソッドの隠蔽(オーバーライドとは別物)

```java
class Parent {
    static void method() { System.out.println("Parent"); }
}
class Child extends Parent {
    static void method() { System.out.println("Child"); }
}
```

- staticメソッドは**オーバーライドではなく隠蔽(hiding)**
- 動的束縛が効かず、**参照変数の型(コンパイル時の型)**によって呼ばれるメソッドが決まる

## 2. 抽象メソッドへのアクセス方法

| アクセス方法 | 可否 | 理由 |
|---|---|---|
| **参照変数経由** | ○ 可能 | インスタンスメソッドなので、参照変数(実体はサブクラス)を通じて呼び出せる |
| **クラス名経由** | × 不可能 | クラス名で直接呼べるのは `static` メソッドのみ |
| **インタフェース名経由** | × 不可能 | インタフェース名で呼べるのも `static` メソッドのみ |

```java
abstract class Animal {
    abstract void cry();
}
class Dog extends Animal {
    void cry() { System.out.println("ワン"); }
}

Animal a = new Dog();
a.cry();          // ○ 参照変数経由:呼び出し可能
// Animal.cry();  // × コンパイルエラー:クラス名経由は不可
```

```java
interface Movable {
    void move();
}
class Car implements Movable {
    public void move() { System.out.println("走る"); }
}

Movable m = new Car();
m.move();          // ○ 参照変数経由
// Movable.move(); // × コンパイルエラー:インタフェース名経由は不可
```

**ポイント**:参照変数経由の呼び出しは、抽象メソッドの本質的な使い方(ポリモーフィズムの実現手段そのもの)。

## 3. 抽象メソッドの呼び出されるプロセス

1. 参照変数の型は**親クラス(またはインタフェース)**、実際に生成するインスタンスは**子クラス**
2. その参照変数を通して、親クラスで定義された抽象メソッド(のシグネチャ)を呼び出す
3. 実行時には、実際に生成されているインスタンス(子クラス)で**オーバーライドされたメソッド**が呼ばれる

```java
Animal a = new Dog();
// 参照変数aの型: Animal(親クラス、コンパイル時の型)
// 実際に生成されるインスタンス: Dog(子クラス)

a.cry();
// コンパイル時: Animalクラスにcry()が定義されているかチェック(あればOK)
// 実行時    : 実際のインスタンス(Dog)のcry()が呼ばれる(動的束縛)
```

**注意点**:`new` するのは常に**具象クラス(子クラス)**。「親クラスの型でインスタンスを生成」ではなく、「親クラス型の参照変数に、子クラスのインスタンスを代入する」が正確な表現(抽象クラス自体はインスタンス化できない)。

## 4. なぜ参照変数を親クラスの型で宣言するのか

### サブクラス型で宣言した場合の問題点

```java
Dog dog = new Dog();
Cat cat = new Cat();
Bird bird = new Bird();

dog.cry();
cat.cry();
bird.cry();
```

→ 動物の種類が増えるたびに、呼び出す側のコードも増え続ける。

### 親クラス型で宣言した場合

```java
Animal[] animals = { new Dog(), new Cat(), new Bird() };

for (Animal a : animals) {
    a.cry();   // Dogでも Catでも Birdでも、同じ1行で済む
}
```

→ 動物の種類が増えても、呼び出す側のコードは一切変更不要。

### メリットまとめ

| 観点 | メリット |
|---|---|
| 配列・コレクションでまとめて扱える | `Animal[]` や `List<Animal>` に異なる子クラスを混在させて格納できる |
| メソッドの引数を共通化できる | `void feed(Animal a)` の1つのメソッドで、Dogでも Catでも受け取れる |
| 拡張に強い(オープン・クローズドの原則) | 新しい動物クラスを追加しても、既存の呼び出し側コードは変更不要 |
| 実装の詳細を隠せる | 呼び出す側は「鳴く」という抽象的な操作だけ知っていればよい |

### メソッド引数での例

```java
void feed(Animal a) {
    a.cry();
}

feed(new Dog());
feed(new Cat());
feed(new Bird());
```

もし引数を `Dog` 型で固定していたら、動物の種類ごとにメソッドを量産する必要が出てくる。

## 5. 実体によって呼ばれるメソッドが変わることの確認

参照変数の型が親クラスでも、**実体(生成したインスタンス)がサブクラス**であれば、呼ばれるのは**サブクラスでオーバーライドされたメソッド**。

```java
abstract class Animal {
    abstract void cry();
}

class Dog extends Animal {
    void cry() { System.out.println("ワン"); }
}

class Cat extends Animal {
    void cry() { System.out.println("ニャー"); }
}

public class Main {
    public static void main(String[] args) {
        Animal a1 = new Dog();
        Animal a2 = new Cat();

        a1.cry();   // 「ワン」← Dogのcry()が呼ばれる
        a2.cry();   // 「ニャー」← Catのcry()が呼ばれる
    }
}
```

### なぜそうなるのか(動的束縛)

| タイミング | 何をチェック/実行するか |
|---|---|
| コンパイル時 | 参照変数の型(`Animal`)に `cry()` というメソッドが存在するか確認するだけ |
| 実行時 | 実際に生成されているインスタンス(`Dog` や `Cat`)を見て、そのクラスの `cry()` を呼び出す |

この「実行時に実体のクラスを見てメソッドを決定する」仕組みを**動的束縛(dynamic binding)**、または**実行時ポリモーフィズム**と呼ぶ。

---

## まとめ

- 抽象メソッドは `static` にできない(束縛タイミングが矛盾するため)
- 抽象メソッドは**参照変数経由でのみ**呼び出せる(クラス名・インタフェース名経由は不可)
- 参照変数の型は親クラス、実体は子クラスで生成するのが基本形
- 親クラス型で宣言することで、コードの再利用性・拡張性が高まる(ポリモーフィズムの狙い)
- 同じ `a.cry()` という呼び出し方でも、**実体のクラスによって動作が変わる**(動的束縛)
