## 1. オーバーライド・オーバーロードの観点からのコンパイルエラー

### 問題のコード

```java
sealed class Super permits Sub {
    double execute(double value) { return value * 1.25; }
}
final class Sub extends Super {
    int execute(double value) { return (int)(value * 1.1); }
    double execute(double v1, double v2) {
        return v1 * v2;
    }
}
```

### エラー内容

```
Sub.java:6: error: execute(double) in Sub cannot override execute(double) in Super
    int execute(double value) { return (int)(value * 1.1); }
        ^
  return type int is not compatible with double
```

### 解説

**オーバーライドかオーバーロードかは「引数の型(シグネチャ)」だけで決まる。戻り値の型は判定基準に含まれない。**

| メソッド | シグネチャ | Superとの関係 |
|---|---|---|
| `Sub.execute(double value)` | `execute(double)` | Superと同一 → **オーバーライド**とみなされる |
| `Sub.execute(double v1, double v2)` | `execute(double, double)` | Superに存在しない → 単なる**オーバーロード** |

- `execute(double, double)` は引数の数が違うため無関係な新規メソッド(オーバーロード)として問題なく成立する。
- `execute(double value)` はシグネチャが完全一致するため、オーバーライドの意図とみなされる。

**なぜ戻り値 `int` がダメなのか(共変戻り値の制約)**

- 共変戻り値型(covariant return type)が許されるのは、**参照型どうし**で、かつ親の戻り値型のサブタイプである場合のみ。
- `int` と `double` はプリミティブ型どうしの関係であり、`int` は `double` のサブタイプではない(むしろ `int→double` は暗黙拡大変換ができる別の関係)。
- そのため「シグネチャが同じ(=オーバーライドすべき)なのに戻り値に互換性がない」と判定され、コンパイルエラーになる。

### 修正方法

**① 本当にオーバーライドしたい場合:戻り値をdoubleに合わせる**
```java
double execute(double value) { return (int)(value * 1.1); }
```

**② オーバーロードにしたい場合:引数の型を変える**
```java
int execute(int value) { return (int)(value * 1.1); }
```

## 2. switch式・例外処理・戻り値の扱いに関するコード読解

### 問題のコード(抜粋)

```java
try {
    execute(list); // list = {"Mon","Sat","Friday","Day","Sun"}
} catch (DataTooLongException | InvalidDataException ex) {
    ex.getMessage();
}
```

`execute` 内では switch式によって `"Mon"→Open`、`"Sat"→Close` を出力し、`"Friday"` で `DataTooLongException` をスローする。

### 出力結果

```
Open Close 
```

### 解説

処理の流れ:

1. `"Mon"` → `Open ` を出力
2. `"Sat"` → `Close ` を出力
3. `"Friday"` → `DataTooLongException("Friday ")` をスロー → **forループはここで中断**され、`"Day"`,`"Sun"` は処理されない
4. `main` の `catch` ブロックで例外を捕捉するが、

```java
catch (DataTooLongException | InvalidDataException ex) {
    ex.getMessage();
}
```

`ex.getMessage()` は**メッセージ文字列を返すだけのメソッド**であり、戻り値をどこにも出力・使用していない。そのため例外メッセージ `"Friday "` は画面に表示されない。

**もし表示させたい場合:**
```java
catch (DataTooLongException | InvalidDataException ex) {
    System.out.print(ex.getMessage());
}
```

## 3. try-catch-finallyの実行順序

### 結論

**tryブロックやcatchブロックの中に`return`があっても、finallyブロックは必ず実行される。**

### finallyが実行されない例外的なケース

- `System.exit()` が呼ばれた場合
- JVMがクラッシュした場合
- tryブロック内が無限ループなどで終わらない場合
- スレッドが強制終了(kill)された場合

### 動作例

```java
static int execute() {
    try {
        System.out.println("try");
        return 1;
    } finally {
        System.out.println("finally");
    }
}
```

出力:
```
try
finally
1
```

`return 1;` の実行後、戻り値をいったん保留してfinallyを実行し、その後で実際に呼び出し元へ値を返す、という流れになる。

### 注意点:finally内のreturn/throwは結果を上書きする

```java
static int execute() {
    try {
        return 1;
    } finally {
        return 2;  // こちらが優先される
    }
}
// 戻り値は 2(1は捨てられる)
```

```java
static int execute() {
    try {
        throw new RuntimeException("try例外");
    } finally {
        throw new RuntimeException("finally例外");
        // こちらが伝播する。「try例外」は握りつぶされる
    }
}
```

### まとめ表

| ケース | finallyは実行される? | 最終結果への影響 |
|---|---|---|
| try内でreturn | される | 通常は問題なし |
| catch内でreturn | される | 通常は問題なし |
| try内で例外throw、catchなし | される | 例外はfinally後に伝播 |
| finally内でreturn/throw | (自身の話) | **try/catchの結果を上書き・握りつぶす**(要注意) |

## 4. デフォルトメソッドの衝突によるコンパイルエラー

### 問題のコード

```java
sealed interface A {
    default int operate(int a, int b) {
        return a * b;
    }
}
sealed interface B {
    default Integer operate(int x, int y) {
        return x += y;
    }
}
non-sealed interface C extends A, B {}
```

### エラー原因

`C` が `A` と `B` の両方を継承した際、**同じシグネチャ`operate(int,int)`を持つデフォルトメソッドが、互換性のない戻り値の型(`int` と `Integer`)を持っている**ため、コンパイルエラーになる。

### 解説

- 通常、インタフェースの多重継承で同一シグネチャのデフォルトメソッドが衝突した場合、サブインタフェース側でオーバーライドして解決できる。

```java
non-sealed interface C extends A, B {
    default int operate(int a, int b) {
        return A.super.operate(a, b); // どちらを使うか明示
    }
}
```

- しかし今回は `A.operate` の戻り値が `int`、`B.operate` の戻り値が `Integer` であり、**共変戻り値の関係にもオートボクシングの考慮にも該当しない**ため、根本的に非互換なメソッドとして扱われる。
- オーバーライドの戻り値互換性の判定では**オートボクシングは考慮されない**ため、`int`と`Integer`は無関係な型とみなされ、オーバーライドによる解決自体が不可能。

### 修正するなら

戻り値の型をどちらも揃える必要がある。

```java
sealed interface B {
    default int operate(int x, int y) {  // Integer → int に変更
        return x + y;
    }
}
```

## 5. 多重継承のルール(クラス vs インタフェース)

### クラス:単一継承のみ

```java
class C extends A, B {}  // ❌ コンパイルエラー
class C extends A {}     // ✅ OK
```

**理由:ひし形継承問題(Diamond Problem)を避けるため。**

```
     Animal
    /      \
  Bird     Fish
    \      /
   FlyingFish
```

`Bird`と`Fish`が`Animal`の同じフィールド/メソッドを異なる形で持っていた場合、`FlyingFish`がどちらを継承すべきか曖昧になる。特に**フィールド(状態)の重複**は解決が困難なため、Javaは言語レベルで多重継承を排除している。

### インタフェース:多重継承が可能

```java
interface C extends A, B {}  // ✅ OK
```

インタフェースは**フィールド(状態)を持たない**ため、フィールドの二重管理のような致命的な曖昧さは発生しない。ただし、**defaultメソッドの実装が衝突する場合はある**(本メモの4章参照)。その場合はサブインタフェース側で明示的にオーバーライドして解決する必要がある。

### implementsは複数OK

```java
class MyClass extends SuperClass implements InterfaceA, InterfaceB {}
// extendsは1つ、implementsは複数可能
```

### まとめ表

| 種類 | 継承元の数 | キーワード |
|---|---|---|
| クラス → クラス | 1つのみ | `extends` |
| インタフェース → インタフェース | 複数OK | `extends` |
| クラス → インタフェース | 複数OK | `implements` |
