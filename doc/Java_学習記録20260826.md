# Java学習セッションまとめ

## 1. Number型のサブクラス

`java.lang.Number`（抽象クラス）の主なサブクラスは以下の3グループに分類できる。

### 基本のラッパークラス（`java.lang`）
- `Byte`
- `Short`
- `Integer`
- `Long`
- `Float`
- `Double`

### 任意精度の数値クラス（`java.math`）
- `BigInteger`（任意精度の整数）
- `BigDecimal`（任意精度の浮動小数点数）

### 並行処理用のアトミッククラス（`java.util.concurrent.atomic`）
- `AtomicInteger`
- `AtomicLong`
- `AtomicIntegerArray`
- `AtomicLongArray`

いずれも`Number`を継承し、`intValue()`、`longValue()`、`floatValue()`、`doubleValue()`などのメソッドを実装している。

## 2. インターフェースの抽象メソッドとオーバーライドの必要性

**結論：抽象クラスの抽象メソッドと同じルールに従う。**

- 具象クラス（`abstract`が付いていないクラス）がインターフェースを実装する場合、インターフェースの抽象メソッド（実装を持たないメソッド）を全て実装しないと**コンパイルエラー**になる。

```java
interface Animal {
    void makeSound(); // 抽象メソッド
}

class Dog implements Animal {
    // makeSound()を実装していない → コンパイルエラー
}
```

### 例外的なケース

1. **サブクラス自身も`abstract`の場合はOK**
   ```java
   abstract class Cat implements Animal {
       // makeSound()を実装しなくてもコンパイルエラーにならない
   }
   ```

2. **`default`メソッドは実装不要**（本体を持つため）
   ```java
   interface Animal {
       default void breathe() {
           System.out.println("呼吸する");
       }
   }
   ```

3. **`static`メソッドは継承・実装の対象外**

4. **複数インターフェースで`default`メソッドが衝突する場合は要オーバーライド**
   ```java
   interface A { default void hello() { System.out.println("A"); } }
   interface B { default void hello() { System.out.println("B"); } }

   class C implements A, B {
       // hello()をオーバーライドしないとコンパイルエラー（曖昧なため）
       public void hello() { A.super.hello(); }
   }
   ```

## 3. 例外の再スローとcatchの挙動

### 対象コード

```java
class UserException extends Exception {
    public UserException(String message) { super(message); }
}
class CustomException extends Exception {
    public CustomException(String message) { super(message); }
}
public class Main {
    public static void main(String... args) {
        try {
            evaluate(1);
        } catch (Exception e) {
            System.out.println(e.getCause());
        }
    }
    public static void evaluate(int value) throws Exception {
        try {
            switch (value) {
                case 1 -> throw new UserException("User Ex!");
                case 2 -> throw new CustomException("Custom Ex!");
            }
        } catch (Exception e) {
            throw new Exception(e.getMessage(), e);
        }
    }
}
```

### 疑問
`evaluate(1)`でthrowされた例外は、なぜ`evaluate`内でキャッチされずに`main`まで伝わるのか？

### 解説

1. `value == 1`のとき`throw new UserException("User Ex!")`が実行される。
2. この`UserException`は`evaluate`内の`try`ブロック内で発生しているため、**同じメソッド内の`catch (Exception e)`で正しくキャッチされている**（`UserException`は`Exception`のサブクラス）。
3. catchブロックの中で`throw new Exception(e.getMessage(), e)`が実行される。
    - これは**新しい`Exception`オブジェクト**を生成して投げている。
    - コンストラクタ`Exception(String message, Throwable cause)`により、元の`UserException`が「原因（cause）」としてセットされる。
4. このcatchブロック自体が新しい例外を投げているだけなので、それをさらに拾う仕組みは`evaluate`内には存在しない。
5. そのため、この新しい`Exception`は`evaluate`の外（`throws Exception`宣言により）へ伝播し、呼び出し元の`main`まで届く。

### 結論
- **最初の例外（`UserException`）は`evaluate`内で確かにキャッチされている。**
- しかし、catchブロックの中でそれを「原因」として包んだ**新しい例外を生成して再スロー**している。
- この新しい例外にはevaluate内にcatchが無いため、`main`まで伝わる。
- 「evaluateでキャッチされない」のではなく、「キャッチされた後、意図的に新しい例外に包んで投げ直している」というのが正確な理解。

### 出力結果
`main`の`e.getCause()`は、原因としてセットされた元の`UserException`を返す。`UserException`が`toString()`をオーバーライドしていない場合、出力はおおよそ以下の形式になる：

```
UserException: User Ex!
```
