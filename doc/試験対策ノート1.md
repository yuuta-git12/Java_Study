# JavaSilver試験対策まとめ

このドキュメントは、演習問題を解きながら整理した「つまずきやすいポイント」と「本番での解き方のコツ」をまとめたものです。

---

## 0. 試験全体の心構え

- 合格ラインは正答率63〜65%程度。40〜50%からでも、頻出の罠パターンを潰せば十分届く。
- **コードの中身(ロジック)を読む前に、修飾子・型・例外の種類など「機械的にチェックできる部分」を先に確認する**のが時間短縮の最大のコツ。
- 「実行結果を答えよ」という問題文でも、**そもそもコンパイルエラーで実行すらされない**選択肢が頻出する。「実行結果」="コンパイルエラー"というケースを常に疑う。

## 1. String / StringBuilder

### 罠1: Stringは不変(immutable)
```java
String s = "abc";
s.concat("def");
System.out.println(s); // "abc" (変わらない)
```
戻り値を代入しない限り元の変数は変化しない。

### 罠2: StringBuilderは可変(mutable)
```java
StringBuilder sb = new StringBuilder("abc");
sb.append("def");
System.out.println(sb); // "abcdef" (直接変わる)
```

### 罠3: よく出るメソッドの仕様
- `substring(begin, end)` → endは含まない(exclusive)
- `indexOf` → 見つからないと `-1`(例外ではない)
- `charAt(int)` → 範囲外は `StringIndexOutOfBoundsException`
- 文字列比較は `equals()`。`new String(...)` が絡む問題で `==` がfalseになる罠に注意
- `StringBuilder` の `reverse()` `insert()` `delete()` `deleteCharAt()` の引数・戻り値の型

### 罠4: `+` 演算子とコンパイルエラー
```java
String s = "abc";
s = s + 1;   // OK "abc1"
s = 1 + s;   // OK "1abc"
int x = "abc"; // コンパイルエラー
```

## 2. コレクション(List, Set, Map)/ ジェネリクス

- `ArrayList`:順序あり・重複可 / `HashSet`:順序保証なし・重複不可 / `LinkedHashSet`:追加順保持 / `TreeSet`:ソートされる
- `HashMap` はキー重複不可(上書きされる)、順序保証なし
- ジェネリクスなしの raw type は**警告のみでコンパイルは通る**(エラーではない点に注意)
- 拡張for文中でのコレクション直接変更は **`ConcurrentModificationException`(実行時エラー)**
- `Map.put()` はキーが既存なら**古い値を返す**、新規なら `null`
- `List.of()` / `Map.of()` は不変 → `add()` すると `UnsupportedOperationException`(実行時エラー)

## 3. オーバーロード解決の速解きテクニック

複数の `method(...)` 定義がある問題では、**中身を読む前に「どの定義が呼ばれるか」を先に確定させる**。

**手順**
1. 呼び出し時の実引数の**型**だけを確認する(変数の宣言型で決まる。中身の実体は関係ない)
2. 型が完全一致する定義があればそれが最優先
3. 完全一致がなければ `Object` 版などの汎用定義が使われる
4. **該当する定義のメソッドの中身だけ**を読む(他は読まない)

**注意点**
- `sb.toString()` のように明示的に型変換すると、その時点で別の型として扱われるため、呼ばれるオーバーロードが変わる
- 短絡評価(`&&` `||`)にも注意。片方がfalse/trueの時点で残りは評価されない

## 4. 例外(検査例外 vs 非検査例外)

### 見分け方
| 種類 | 代表例 | throws宣言 |
|---|---|---|
| 検査例外(checked) | `Exception`, `IOException` | **必須**(なければコンパイルエラー) |
| 非検査例外(unchecked) | `RuntimeException` とそのサブクラス | 不要 |

### 検査例外は呼び出し階層を遡って伝播する
```
main() → methodA() → methodB()
```
`methodB` が検査例外を投げて未処理なら、**呼び出し元の `methodA` にも `main` にも `throws` が必要**。
どこかで `try-catch` すれば、それより上流では `throws` は不要になる。

### 本番でのチェック手順
1. コード中に `throw new ○○` があれば、○○が `RuntimeException` 系かそれ以外かを先に確認
2. 検査例外なら、そのメソッドと**呼び出し元すべて**に `throws` があるか確認
3. なければ即「コンパイルエラー」を疑う

## 5. sealed / permits

### 基本ルール
`permits` が許可するのは **直接のサブタイプ関係のみ**(間接的な継承チェーンは対象外)。

| sealed型 | permitted側 | キーワード | 許可の種類 |
|---|---|---|---|
| `sealed interface` | クラス | `implements` | 実装の許可 |
| `sealed interface` | インターフェース | `extends` | 拡張の許可 |
| `sealed class` | クラス | `extends` | 拡張の許可 |

### permitted側は必ず次のどれかを宣言
| permitted対象 | 選べるキーワード |
|---|---|
| クラス | `final`, `sealed`, `non-sealed` |
| インターフェース | `sealed`, `non-sealed`(`final`は不可) |

### 間接継承の罠
```java
sealed interface X permits A, B {}
final class A implements X {}
non-sealed interface B extends X {}
interface C extends B {}
```
`class A implements C` のように **X を直接実装せず** C だけを実装するとコンパイルエラー。
`permits` は「直接 `implements X` / `extends X` と書かれていること」を要求するため。

## 6. final / private とオーバーライド

- **`final` メソッド** → オーバーライド禁止。サブクラスで同名メソッドを定義するとコンパイルエラー
- **`private` メソッド** → そもそも継承されない。サブクラスで同名メソッドを書いても、それは無関係な別メソッド(オーバーライドではない)
- **`static` メソッド** → オーバーライドではなく「隠蔽(hiding)」
- オーバーライド時にアクセス修飾子を**狭める**(`public`→`protected`など)とコンパイルエラー
- **フィールドはポリモーフィズムが効かない**(静的型で決まる)。オーバーライドされるのはメソッドだけ

### 読む順序のコツ
1. まず `final` / `private` / `static` の修飾子だけを全メンバーについてスキャン → 矛盾があれば即コンパイルエラーで終了
2. 問題なければフィールドの隠蔽とメソッドのオーバーライドの違いに注意
3. それでも問題なければ実際の値を追って処理を実行

## 7. 総合チェックリスト(本番で1問ずつ使う)

- [ ] `throw` があれば、検査例外か非検査例外かを先に確認
- [ ] 検査例外なら呼び出し元すべてに `throws` があるか確認
- [ ] `final` / `private` / `static` の修飾子とオーバーライドの矛盾がないか確認
- [ ] 複数の同名メソッド(オーバーロード)があれば、引数の**型**だけで先にどれが呼ばれるか決める
- [ ] `sealed` / `permits` が絡む場合、直接関係か間接関係かを確認
- [ ] String操作は「戻り値を代入しているか」、StringBuilderは「直接変更されているか」を確認
- [ ] 上記すべてクリアして初めて、実際のロジック(値の流れ)を追う
